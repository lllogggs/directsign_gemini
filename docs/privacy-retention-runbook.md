# 개인정보 보유·파기 운영 절차

이 문서는 연락미 운영 데이터의 자동 파기, 회원 탈퇴, 법적 보존, 백업 복원 시 재파기 절차를 정한다. 운영 환경에서는 매시간 30분에 `CRON_SECRET`으로 인증된 `/api/cron/privacy-retention`만 자동 파기를 실행한다.

법적 보존이 활성화된 대상은 자동 파기에서 제외한다. 보존 사유가 해제되거나 만료되면 다음 실행에서 다시 평가한다. 법적 보존 사유에는 자유형 개인정보를 적지 않고 사건·운영 티켓의 비식별 참조만 기록한다.

## 매시간 실행 순서

1. 확인 후 30일이 지난 네이버 블로그 캠페인 지원 조건 확인값과 1년이 지난 네이버 인플루언서 자동 확인·본인 확인 재사용 기록을 비공개 저장소에서 삭제하고, 캠페인 종료·제출 마감 후 90일이 지난 신청 동의 증적에서 휴대전화·이메일 값을 삭제한다.
2. `run_privacy_retention`이 만료 대상을 범주별 독립 배치로 선별하고 삭제할 Storage 객체를 큐에 적재한다.
3. 서버는 삭제 직전에 작업 lease와 법적 보존 상태를 다시 승인받은 뒤 Storage API로 허용된 버킷과 경로의 객체만 삭제한다. `storage.objects` 메타데이터를 직접 삭제하지 않는다. 삭제가 진행 중인 대상에는 새 법적 보존을 동시에 설정할 수 없고 운영자가 작업 종료 뒤 다시 시도한다.
4. 객체 삭제 성공과 유효한 작업 lease를 큐에 기록한다. 실패 항목은 오류 종류만 남기고 자동 재시도하며, 10회 실패한 항목은 운영자가 원인을 고친 뒤 같은 큐 항목을 재개한다.
5. 탈퇴 처리 중인 Supabase Auth 사용자를 하드 삭제하고 완료 상태로 전환한다.
6. `run_privacy_retention`을 다시 실행해 파일 삭제가 확인된 데이터베이스 묶음만 삭제한다.
7. 만료·저장소·Auth 잔여 수량을 식별자 없이 다시 집계한다. 남은 건이나 실패 건이 있으면 운영 알림을 남기고 다음 매시간 작업에서 계속 처리한다.
8. 실행 기록에는 범주별 건수만 남기며 이메일, IP, 파일 경로, 토큰, 계약 식별자는 로그에 남기지 않는다.

`contract_events`와 `support_access_events`의 append-only 보호는 일반 요청에서 유지된다. 보유기간과 법적 보존 상태를 다시 확인한 보안 정의 파기 함수의 트랜잭션 안에서만 삭제 예외가 켜진다.

운영 저장파일은 Supabase Storage 경로만 자동 삭제한다. 레거시 `local_file` 참조가 발견되면 데이터베이스 원본 삭제를 중단하고, 운영자가 실제 로컬 파일을 확인·파기한 뒤 참조를 정규화해 다시 실행한다.

## 회원 탈퇴

- 회원은 계정 설정에서 `탈퇴`를 정확히 입력하고 최근 10분 이내 비밀번호 재확인을 거친다.
- 요청은 Idempotency-Key로 중복 실행을 막는다.
- 공개 프로필, 선택 연결, 세션, 최근 인증 권한과 비보존 데이터의 이용·공개를 즉시 중단한다. Storage 장애가 있으면 공개 연결을 먼저 제거하고 물리 객체 삭제를 자동 재시도한다.
- 서명·계약 증빙은 계정과 연결을 끊고 비공개 제한 보관한다. 보유기간이 끝나면 동일한 자동 파기 절차를 따른다.
- Google OAuth 공급자 철회는 먼저 시도하고, 공급자 장애와 관계없이 로컬 암호화 토큰은 즉시 삭제한다.
- Supabase Auth 삭제가 일시 실패해도 계정은 이용할 수 없으며 자동 작업이 하드 삭제를 재시도한다.
- 탈퇴한 Auth UUID와 HMAC 해시는 탈퇴 재처리·백업 복원 방지를 위해 1년간 보관한다. 단, 보존 계약과 연결된 단독 조직 정리에 필요한 내부 조직 ID는 계약·법적 보존 종료 후 정리가 끝날 때까지 남긴다.
- 브라우저 JWT의 원시 테이블 조회 권한은 회수되어 있으므로 전역 로그아웃 직전 발급된 access token도 보존 계약·인증 자료를 Data API로 직접 읽을 수 없다.

## 배포 전·정기 확인

```powershell
supabase migration list --linked
supabase db push --linked --dry-run
supabase db lint --linked --schema public --level error --fail-on error
supabase backups list --project-ref pztalpidqdbzgwyofobj --output json
```

- dry-run에는 승인된 새 migration만 보여야 한다.
- 백업 목록은 최근 7개 일일 물리 백업만 존재하고 PITR가 비활성인지 확인한다.
- 요금제나 PITR 설정이 바뀌면 실제 보존기간을 다시 확인하고 개인정보 처리방침도 같은 배포에서 수정한다.
- Supabase Storage 객체는 DB 백업에 포함되지 않는다는 공급자 정책을 정기적으로 재확인한다.

## 백업 복원

1. 복원 직전 현재 운영 DB의 완료된 `privacy_erasure_requests.subject_hash` 목록과 활성 법적 보존 목록을 접근 제한된 운영 산출물로 내보낸다. 원문 사용자 식별자나 이메일은 내보내지 않는다.
2. 백업은 격리 환경에 복원하고 고객 트래픽을 연결하지 않는다.
3. 복원된 profile UUID를 서버의 동일 HMAC 규칙으로 해시해 탈퇴 해시 목록과 대조한다.
4. 일치 계정에 회원 탈퇴 절차를 재적용하고, 만료 대상 파기와 Storage 큐를 모두 완료한다.
5. 익명·회원·운영자 접근, 공개 프로필, Auth 로그인, Storage 객체가 다시 노출되지 않는지 검증한 뒤에만 트래픽을 전환한다.
6. 임시 내보내기 산출물은 복원 검증 완료 즉시 안전하게 삭제한다.

복원 시점보다 나중에 접수된 탈퇴를 재적용하지 않은 백업을 운영에 공개해서는 안 된다.
